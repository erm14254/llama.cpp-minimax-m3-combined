### The whole Q path is byte-exact

`q_a_proj`, `q_a_layernorm` and `q_b_proj` are identical to the HF Blackwell

### `kv_a_proj_with_mqa` is a pure output boundary

Rounding the C++ F32 output to BF16 makes it **exactly** equal to HF — 100.00%

### `kv_a_layernorm` is the first genuine divergence — and it is explained

This is the reading that sat below the Ampere noise floor and genuinely
required this run. `analyze_longcat_attn0_kv_a_norm_semantics.py` reconstructs
the norm offline from the GGUF weight the C++ run actually loaded:

1. **Sanity** — the offline F32 model reproduces the **C++** surface at
   rel-RMSE 0, 100.00% exact. The reconstruction and weight are correct.
2. **Control** — `bf16(C++ kv_a_proj[:, :512]) == HF kv_a_proj[:, :512]` is
   `True`. The upstream input differs *only* by the rounding boundary above.
3. **Sweep** — feeding HF's own byte-identical BF16 input through llama.cpp's
   F32 norm still does **not** reproduce HF (rel-RMSE 0.00208, 0% exact). So
   the divergence is in the norm's precision semantics, not its input.

| Cast ordering (eps=1e-6) | rel-RMSE | exact% |
|---|---|---|
| A `f32(norm) * f32(w)` → f32 — **llama.cpp today** | 0.00207546 | 0.00% |
| B `bf16( f32(norm) * f32(w) )` | 0.000359351 | 68.59% |
| **C `bf16( bf16(norm) * f32(w) )`** | **0** | **100.00%** |
| **D `bf16( bf16(norm) * bf16(w) )`** — HF RMSNorm pattern | **0** | **100.00%** |
| E `bf16(norm) * bf16(w)` → f32 | 0.0010619 | 2.54% |

**HF rounds the normalized activation to BF16 *before* the weight multiply,
and rounds the product to BF16. llama.cpp keeps both in F32.** That single
ordering difference accounts for the surface *exactly* — max_abs 0.

C and D coincide because the norm weight is already 100% on the BF16 lattice.
eps 1e-6 and 1e-8 both reproduce exactly; **1e-5 is excluded** (rel-RMSE

## Environment finding — cuBLAS version silently breaks every gate

The first gated run **failed**: `logical0_attn0_resid` came out
`49d729e16b09b7d113e1d774851364b4c31ee1ff98608505cbe52122824fc928` while both
upstream anchors passed and placement was bit-identical to the frozen run.

Running the **historical** `llama-debug.exe` — the exact binary that produced
`2c804a35…` on 2026-08-15 — reproduced the same `49d729e1…`. So the rebuild was
never at fault; the frozen residual had stopped being reproducible on this
machine.

Cause: `ggml-cuda.dll` imports **`cublas64_13.dll` by bare name**, and this
machine's `PATH` lists `CUDA\v13.0\bin\x64` **before** `v13.2`. The process was
loading cuBLAS **6.14.11.1300** (v13.0) instead of the **6.14.11.1330** (v13.2)
the build targets. Prepending the v13.2 directory restored `2c804a35…`
byte-exact.

The failure signature is diagnostic in itself: custom elementwise kernels
(`inp_embd_ngram`, `attn_norm-0`) stayed byte-exact while the GEMM-dependent
residual moved — exactly what a cuBLAS kernel-selection change produces.

> **Every future run on this workstation must pin cuBLAS to v13.2**, e.g. by
> prepending `C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.2\bin\x64`
> to `PATH` for the child process. Without it the frozen gates fail silently
> and any comparison is invalid.
